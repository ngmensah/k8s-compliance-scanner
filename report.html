🔴 Issue #1: Privileged Container Mode Enabled



securityContext:
  privileged: true   # ← THIS LINE

**Severity:** `HIGH`


What's wrong:

A privileged container has nearly unrestricted access to the host system. It can modify kernel parameters, access all host devices, load kernel modules, and effectively escape the container boundary entirely.


Compliance impact:

  • **CIS Kubernetes Benchmark** (5.2.1): Explicitly requires privileged containers to be disallowed
  • **NIST SP 800-190**: Container environments must enforce isolation boundaries
  • **PCI-DSS** (Requirement 6): Systems must be protected from known vulnerabilities — privileged containers are a well-known attack vector
  • **SOC 2**: Violates the principle of least privilege required by the Common Criteria

    • Fix:

    
securityContext:
  privileged: false   # Explicitly set to false
  allowPrivilegeEscalation: false   # Also add this
  capabilities:
    drop:
      - ALL   # Drop all capabilities, add back only what's needed
    add:
      - NET_BIND_SERVICE   # Example: only if binding to port < 1024


    🔴 Issue #2: Container Running as Root (UID 0)


    
securityContext:
  runAsUser: 0   # ← Root user

    **Severity:** `HIGH`


    What's wrong:

    The container process runs as the root user. If an attacker exploits the application, they immediately have root-level access inside the container. Combined with the privileged flag, this becomes a full host compromise path.


    Compliance impact:

  • **CIS Kubernetes Benchmark** (5.2.6): Containers should not run as root
  • **NIST SP 800-53 (AC-6)**: Least privilege principle — processes should run with minimum necessary permissions
  • **PCI-DSS** (Requirement 7): Access must be restricted on a need-to-know basis
  • **HIPAA**: Inadequate access controls create unacceptable risk to protected health information systems

    • Fix:

    
securityContext:
  runAsUser: 1000        # Use a non-root UID
  runAsGroup: 1000       # Set group explicitly
  runAsNonRoot: true     # Kubernetes will reject startup if the image tries to run as root
  allowPrivilegeEscalation: false


    🔴 Issue #3: Plaintext Secret in Environment Variable


    
env:
  - name: DB_PASSWORD
    value: "supersecretpassword123"   # ← Hardcoded secret

    **Severity:** `HIGH`


    What's wrong:

    The database password is hardcoded directly in the manifest in plaintext. This means:

    1. The secret is stored in version control (likely)

    2. It's visible to anyone who can run `kubectl describe pod`

    3. It's stored unencrypted in etcd by default

    4. It will appear in any CI/CD logs that print manifests


    Compliance impact:

  • **PCI-DSS** (Requirement 3 & 8): Cardholder data and credentials must be protected — hardcoded credentials are an automatic audit failure
  • **SOC 2 (CC6.1)**: Logical access controls are required for sensitive data
  • **GDPR**: If this connects to a database with personal data, inadequate credential management is a reportable risk
  • **OWASP Top 10** (A02 - Cryptographic Failures): Hardcoded credentials are a well-documented critical risk

    • Fix:

    
# Step 1: Create the secret properly (ideally via a secrets manager, not CLI)
# kubectl create secret generic db-credentials --from-literal=password='supersecretpassword123'

# Step 2: Reference it in the manifest — never store the value inline
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-credentials
        key: password

# Additional recommendation: Enable etcd encryption at rest in your cluster config
# and consider an external secrets operator (e.g., External Secrets Operator with 
# HashiCorp Vault, AWS Secrets Manager, or Azure Key Vault)


    🟠 Issue #4: Host Network Access Enabled


    
hostNetwork: true   # ← Direct access to host network stack

    **Severity:** `HIGH` / `MEDIUM` (HIGH in multi-tenant clusters)


    What's wrong:

    The container shares the host node's network namespace. It can see and bind to any port on the host, listen to all network traffic on the node, and bypass Kubernetes NetworkPolicy controls entirely.


    Compliance impact:

  • **CIS Kubernetes Benchmark** (5.2.4): Host networking should be disallowed
  • **NIST SP 800-190**: Containers must maintain network isolation
  • **PCI-DSS** (Requirement 1): Network segmentation controls are undermined — a container that can sniff host network traffic could capture data in transit

    • Fix:

    
spec:
  hostNetwork: false   # Default is false — simply remove the line or set explicitly
  
  # If inter-pod communication is needed, use Kubernetes Services
  # If specific network policies are needed, use NetworkPolicy resources:

---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: sample-app-netpol
spec:
  podSelector:
    matchLabels:
      app: sample-app
  policyTypes:
    - Ingress
    - Egress
  ingress:
    - ports:
        - port: 80


    🟠 Issue #5: Host PID Namespace Shared


    
hostPID: true   # ← Sees all host processes

    **Severity:** `HIGH` / `MEDIUM`


    What's wrong:

    The container can see every process running on the host node. This allows:

  • Reading memory of other processes (`/proc//mem`)
  • Sending signals to host processes (e.g., `kill` critical system processes)
  • Discovering sensitive information from process arguments (passwords passed via CLI args, etc.)

    • Compliance impact:

  • **CIS Kubernetes Benchmark** (5.2.2): Host PID sharing should be disallowed
  • **NIST SP 800-53 (SC-39)**: Process isolation must be maintained
  • **SOC 2**: Violates isolation controls between workloads — particularly dangerous in shared/multi-tenant clusters

    • Fix:

    
spec:
  hostPID: false   # Default is false — remove the line or set explicitly


    🟡 Issue #6: Unpinned Image Tag (`latest`)


    
image: nginx:latest   # ← Floating tag

    **Severity:** `MEDIUM`


    What's wrong:

    Using `latest` means:

    1. The exact image pulled is non-deterministic and changes over time

    2. You cannot guarantee which version (and which vulnerabilities) are running

    3. Rollbacks become unreliable

    4. Security scanning results may not match what's actually deployed


    Compliance impact:

  • **NIST SP 800-190**: Software supply chain integrity requires knowing exactly what you're running
  • **PCI-DSS** (Requirement 6.3): Vulnerability management requires knowing software versions
  • **SOC 2 (CC7.1)**: Change management requires deterministic, auditable deployments
  • **CIS Benchmark** (5.5.1): Use approved and version-pinned base images

    • Fix:

    
# Pin to a specific immutable digest or at minimum a specific version
image: nginx:1.27.0   # Specific version tag

# Even better — pin to the digest (truly immutable):
image: nginx@sha256:a484819eb60211f5299034ac80f6a681b06f89e65866ce91f356ed7c72af059c
